# ADR-0014: Decision report, scheduling and the refresh workflow

**Status:** accepted, 2026-11-06

## Context

Milestone 4 adds the deliverable a treasurer reads (`reports/decision_report.md`), a way
to run the pipeline on a schedule, and a way to keep the committed data current. Three
questions: should the report recompute anything; how should the pipeline be scheduled in
production versus in this repository; and how should a data refresh reach `main`.

## Decision

* **The report computes nothing.** `fxrisk report` reads the DuckDB tables the earlier
  stages persisted (`hedge_headline`, `hedge_recommendation`, `hedge_frontier`,
  `hedge_reference`, `policy_backtest_*`, `policy_decisions`, `forecast_eval`,
  `forecast_latest`, `risk_results`, `stress_results`, `var_backtest_results`) plus three
  small views in `sql/110_report_views.sql`, re-uses the figures the stages drew, and
  draws two more from exposure views (the waterfall and its monthly-average history).
  Prose is templated around the numbers so a refreshed data set rewrites the argument.
  The quality section re-reads `reports/quality_report.md` rather than re-running the
  checks. Consequence: the report can never disagree with the stage reports, and a reader
  can trace every number to a table in `data/fxrisk.duckdb`.
* **Report order follows the brief:** question and answer first, then data and quality,
  exposure waterfall, forecast calibration, VaR/ES with coverage verdicts, stress,
  frontier and ratios, out-of-sample policy performance (with March/April 2020 and
  September/October 2022 broken out), and a closing "what this model does not know"
  section that quotes the model's own weaknesses with numbers.
* **Airflow DAG is illustrative** (`dags/fxrisk_daily.py`): one `BashOperator` per CLI
  stage, strictly linear, weekday 06:30 New York, no catch-up, retries only on the
  network stage, quality as a gate. It is not executed in CI (backlog B7): Airflow is a
  heavy dependency whose value here is to show how the stages would be sequenced, not to
  test the stages, which the CLI tests already do. `tests/test_dag.py` parses the file
  and asserts its stage list equals the CLI's `all` order, so the two cannot drift.
* **Scheduled refresh runs in GitHub Actions and opens a pull request**
  (`.github/workflows/refresh.yml`, Mondays 11:30 UTC and on demand). It re-downloads
  every series with the `FRED_API_KEY` secret, runs the pipeline, and commits
  `data/cache/**` and `reports/**` to a branch via `peter-evans/create-pull-request`. It
  never pushes to `main`: the PR runs the normal CI from the refreshed cache and a person
  merges it after reading `reports/alerts.md`. A quality FAIL still opens the PR, labelled
  as failed, with the downstream stages skipped, so that a broken source is seen rather
  than silently retried the following week. Repository settings required: the secret,
  workflow permissions read/write, and "allow GitHub Actions to create pull requests".
* **Figures in the report are static PNGs** drawn with matplotlib, committed with the
  report so that the GitHub rendering is self-contained. The two new ones use a single
  blue ramp (gross, net, net of hedges are one quantity at three stages of netting), the
  policy figures keep the four fixed policy colours from milestone 3.

## Consequences

* `fxrisk all` ends with `report`; CI runs it and uploads the report as an artifact.
* The committed `reports/` directory is regenerated by the weekly PR, so its numbers can
  move; the README's headline quotes the report rather than hard-coding values that would
  go stale (the README itself is edited by hand and says so).
* Because the report reads tables, adding a section means adding a persisted table in
  the stage that knows the numbers, then a renderer; `tests/test_report.py` tests the
  renderer on hand-made frames and the loader against the real database when present.
